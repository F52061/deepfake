§2  freeze bug 已修 + 冒烟 v2 验证
================================================================================
修法: 在 `apply_fix_a()` **之后**统一再冻结一次（phase2_common.build_model_variant）。
原因: apply_fix_a 内部 `nn.Linear(...)` 默认 requires_grad=True，绕过了之前的冻结。

冒烟 v2 实测（phase2_smoke_log.txt）:
  fix         trainable = 52 张量 / 0.5767M  (bridge=50, output=2, other=0)
  randbridge  trainable =  2 张量 / 0.0033M  (bridge= 0, output=2, other=0)
              NAMES = ['output.weight', 'output.bias']
              [FREEZE-FIX CHECK] -> **PASS**
  nofix       trainable = 54 张量 / 0.5767M  (bridge=52, output=2, other=0)

关于 fix(50) vs nofix(52) 的 2 个张量差异 —— **这是干预本身，不是 bug**:
  逐名对比后，两者唯一的差异是 nofix 多出
  `bridge_adapter_proj.bridge_adapter_proj.2.weight` 与 `.bias`
  —— 即**只有在"未修复"模型里才存在的那个 LayerNorm(1)**。
  fix 组把它删掉了，所以自然少 2 个。两者其余 50 个桥张量完全相同。
  （另注: 该 LayerNorm(1).weight 的梯度可证明恒为 0，因为它的归一化输入恒为 0；
    只有它的 bias 会移动。所以这 2 个张量里实际只有 1 个在动。）
  -> 我冒烟里那条 "fix vs nofix 桥张量数必须相等" 的检查打印 FAIL，
     是我那条检查写得太粗；**按构造它本就应该差 2**。特此说明，不当成故障。

800 行 test 全集两类检查（Coordinator 指定）:
  n=800, y counts = {0: 400, 1: 400} -> **两类都有，PASS**
  （phase-1 冒烟的 nan 纯粹是我当时"取前 200 行"造成的: 前 200 行 y 全是 0，
    后 200 行 y 全是 1。全集没问题，phase-1 的 0.9880 成立。）
  修正子集后冒烟 v2 的 ffpp_test = 0.9899 / 0.9902 / 0.9899（三组）。
  **注意: 冒烟只训练 180 张 / 6 步，这些 AUC 无科学意义，仅验证"能出数"。**

§3  长口径标定（授权执行）
================================================================================
方法: 2100 张（每类 420）、70 个真实 batch、走完整生产路径
      (BalancedBatchSampler -> balanced_collate -> fwd -> CE -> bwd ->
       clip_grad_norm_ -> AdamW.step)，`torch.cuda.synchronize()` 后才停表。
      无 half_hook（纯计时）。

  组             ms/img      epoch(h)    每run(h)
  fix            85.35       2.553       2.746
  randbridge     68.92       2.062       2.253
  nofix          79.70       2.384       2.576
  均值           77.99       2.333       2.525

  每 run = epoch + 半程评估 + 收尾评估 + 建模 + 2 次存档
      评估 = 4500 张 @ 74.3 ms/img(phase-1 实测) = 5.6 min = 0.093 h

  >>> 9 次运行 = **22.73 h**（均值口径）
                最坏 24.72 h / 最好 20.28 h
  >>> 用户批准 21.2 h -> **超出 1.53 h**

【超支归因（关键）】
  phase-1 预测: epoch 2.36 h + 1 次评估 0.094 h = 2.454 h/run -> 22.1 h
  新规格加第 2 次评估: +0.093 h/run -> 2.547 h/run -> 22.9 h
  本次实测: 2.525 h/run -> 22.73 h
  **误差 <1%，吞吐模型被验证是准的。超支 100% 来自新加的"半程评估"，
  不是机器变慢。** 实测 epoch 均值 2.333 h 甚至比 phase-1 预测的 2.36 h 快 1.1%。

【必须报告的异常: fix 组比 nofix 组慢 6%，原因未定】
  fix 85.35 vs nofix 79.70 ms/img，但两者可训练张量数几乎相同（50 vs 52）、
  计算图完全相同。三次独立测量里 fix **每次都是最慢**（88.4 / 82.6 / 85.35），
  randbridge **每次都是最快**（69.8 / 70.5 / 68.92）。
  randbridge 快是合理的（只 2 个可训练张量，没有 50 张量的 clip_grad_norm_/AdamW）。
  但 fix vs nofix 的 6% 差异**我无法解释**，最可能是运行顺序/热效应
  （fix 三次都是第一个跑）或测量噪声。
  影响: 若 fix 的真实成本与 nofix 同为 ~80 ms/img，均值降到 ~76.3 -> 22.2 h，
  **仍然超出 21.2 h**，所以不改变结论。
