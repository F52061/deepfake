V1x. SECONDARY FINDING -- WHY IS clip_reduction.weight GRADIENT EXACTLY ZERO?
     (not part of the original V-spec; surfaced by the V1 contrast column)
----------------------------------------------------------------------------------------------------
  Hypothesis, from source: vit_m2f2_detector_bridge.py L157-161 defines
      BridgeAdapter_Proj_ViT.bridge_adapter_proj = Sequential(View(-1,64), Linear(64,1),
      LayerNorm(1)).
  nn.LayerNorm(1) normalizes a 1-element vector: mean == the element, so (x - mean) == 0
  EXACTLY, rstd*0 == 0, and the layer output reduces to its bias. Consequently the pooling
  output is a constant that does not depend on the bridge features at all.

  Micro-test, nn.LayerNorm(1) on 512 random scalars (spread 179.760712):
    output spread = 0.000e+00   (bias = 0.018901)
    -> CONFIRMED: output is exactly constant

  Same effect inside the real model:
    DISCRIMINATOR -- the Linear(64,1) that feeds LayerNorm(1) produces shape (37056, 1)
      with spread 3.554970e-01 over all tokens/images, and its weight is NON-ZERO
      (|w|max=2.687270e-02, ||w||=8.084483e-02).
      So the input to LayerNorm(1) really does vary; the collapse happens IN LayerNorm(1).
    the model's LayerNorm(1) has weight=[0.999358057975769] bias=1.8901443109e-02;
      output = (x-mean)*rstd*weight + bias = 0*weight + bias = bias, a constant.
    inner per-token output shape (37056, 1), spread over ALL 37056 entries = 0.000e+00
      -> the per-token pooled scalar is the SAME for every token and every image.
    bridge embedding (the 128-d clip_adapt_embed input) shape (16, 128)
      pairwise max deviation within one batch of 16 : 0.000e+00
      max|A - B| across two DIFFERENT batches of 16 : 0.000e+00 (L2 = 0.000e+00)

  CONSEQUENCE: the 128 fusion dims [768:896] receive a vector that is identical for every
  image. The classifier can only use it as a constant offset (absorbed into output.bias),

CAVEATS
----------------------------------------------------------------------------------------------------
  1. This experiment tests the ARCHITECTURE CODE PATH, not every possible usage. It shows the
     text branch's output cannot reach `output` in this forward(). Any consumer of it would
     have to read model.clip_text_encoder()/text_proj directly outside forward() (no caller
     does so in this repo's forward path) or a subclass/different checkpoint could change it.
  2. Everything is done with ONE checkpoint (bridge_v2_phase1.pth). The conclusion is
     'these weights, this code' -- a differently-built model would need its own test.
  3. V1 used loss = out.sum() (no labels). That is a valid loss for asking 'does autograd
     build a path from these params to the logits'; it is NOT the training loss. Any loss
     that is a function of `output` gives the same answer, since reachability is a property
     of the graph, not of the loss value.
  4. V1 grad=None means 'not reached by this graph'. Because text_proj IS called in forward
     (so it is in the graph as a dead end) the None is informative; but the experiment cannot
     distinguish 'never trained' from 'trained in a different code path / different script'.
     A separate history check (Stage-1/2/3 training scripts) would be needed to claim the
     parameters were never updated by ANY training run.
  5. V3.2's literal 'max per-sample deviation across the batch' is vacuous because the tensor
     has exactly one row; the batch-size-independence check (batch 1 vs 8 vs 16) is the
     substantive substitute and is reported alongside it.
  6. Bitwise comparisons (V2, V3.3) are meaningful only because the unpatched repeat-forward
     determinism control came back bitwise identical; that control is reported.
  7. V1b statistics are recorded from the checkpoint as loaded; the equally-loaded identical
     values in text_proj being initialized elsewhere in this repo (init_weights uses
     normal_(std=0.01) / bias 0) were NOT verified against the checkpoint in this run, so no
     claim is made about how these values arose.
  7b. V1's contrast expectation was NOT fully met: clip_reduction.weight has an exactly-zero
      gradient. This does not weaken the text-branch conclusion (the text branch has NO grad
      tensor at all, which is a different and stronger signal) but it means the V-spec's stated
      expectation for the contrast group is falsified for 1 of its 4 members.
  7c. The V1x bridge-constancy finding rests on one forward graph of this checkpoint at fp32.
      It is measured (not inferred) for the pooled token / 128-d embedding / LayerNorm(1) micro-
      test, but the claim 'the bridge branch is dead' is scoped to this code path + checkpoint.
      Whether LayerNorm(1) was intentional in the original EfficientNet BridgeAdapter_Proj was
      not checked here.
  8. Single GPU (physical card 2), fp32 only, batch<=16; no fp16/bf16 numerics were tested.
  9. V5 is checkpoint-only: it characterizes the read-out direction d, not the model's
     behaviour on data. The 0% text share is a property of the concat order + Linear input
     width, which is structural, not weight-dependent.
